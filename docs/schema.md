# Talksasa Pay data model, in plain language

This page explains what the database stores and the rules it enforces. The
SQL lives in `db/migrations/000001_core.up.sql`.

## The big picture

```
products ──< payer_accounts ──< payment_requests
   │               │                    ▲
   │               │                    │ allocations (where each shilling went)
   │               └──< transactions ───┘
   └── product_api_keys
audit_log: who did what (tamper-evident)
```

- A **product** is one of Talksasa's own businesses (ISP Billing = `BILL`,
  Cloud Hosting = `HOST`). Adding a product means adding a row and issuing an
  API key. No code changes are needed.
- A **payer account** is one of that product's customers. It has a permanent
  account number such as `HOST-4471`, which customers type on the M-Pesa menu.
- A **payment request** is a bill the product wants paid, e.g. "Invoice
  INV-2041, KES 2,500".
- A **transaction** is real money that moved: an M-Pesa receipt coming in, or
  (later) a refund going out.
- An **allocation** records which request(s), or the credit balance, each
  shilling of a transaction went to.

There is no table or column for paying money out *to a product*. Everything
collected is Talksasa revenue (see `docs/adr/0001-revenue-only.md`).

## Tables

### products
Name, account prefix (2–6 capital letters, unique, can never change), webhook
URL, webhook signing secret and status (`active` / `suspended`). The webhook
secret is **encrypted** (AES-256-GCM, master key kept outside the database).
A suspended product's API keys stop working at once.

### product_api_keys
Keys look like `tsp_live_<key id>_<secret>`. We store only the key id and a
keyed hash of the secret, so the full key exists only at the moment it is
issued. A product can have several active keys, which lets you rotate without
downtime. Keys can expire and be revoked. A revoked key cannot be
un-revoked.

### payer_accounts and payer_phones
- `external_ref` is the product's own customer/tenant id, unique within the
  product. Two products may reuse the same id; they are still separate payers.
- `account_number` is generated by Talksasa Pay: prefix, hyphen, a
  per-product counter starting at 100, then one **check digit**. The first
  accounts are four digits long (`HOST-1003`, ...). The counter only moves
  forward and rows are never deleted, so a number is **never reused**.
- **Typing tolerance.** Matching ignores case, spaces and hyphens, so
  `host4471`, `HOST 4471` and `Host-4471` all match `HOST-4471`. The check
  digit catches every single wrong digit and every swap of two neighbouring
  digits. A mistyped number therefore goes to the suspense queue instead of
  crediting a stranger.
- `credit_balance` is the payer's prepaid credit (from overpayments).
- Phones are stored as `2547XXXXXXXX` or `2541XXXXXXXX`; the first is the
  primary. Phones are the one personal detail that can be deleted when a
  customer changes number.

### payment_requests
Amount (whole KES), the product's reference, a description, an optional expiry
date, and an idempotency key from the product, so retrying the same API call
never creates a second bill. Status:

| Status | Meaning |
|---|---|
| `open` | nothing paid yet |
| `partially_paid` | some paid, some outstanding |
| `paid` | fully paid |
| `cancelled` | closed by the product before any payment |
| `expired` | passed its expiry date before any payment |

The database refuses a status that disagrees with the amount paid, e.g.
"paid" with KES 0 allocated. Only untouched (`open`) requests can be cancelled
or expire; a partially paid request stays payable. Only one open request may
use a given product reference at a time.

### transactions (the ledger)
One row per money movement: direction (`in` / `out`), channel (`mpesa_stk`,
`mpesa_c2b`, `mpesa_b2c`, later card), M-Pesa receipt, amount, phone, the
account number as the customer typed it, status, the provider's raw message,
and the payer and request it matched.

The rules, enforced by the database itself:

- **A receipt is recorded once.** All M-Pesa channels share one receipt
  space, so the same receipt can't appear twice, even if it arrives once by
  STK callback and again by statement import. A repeat callback changes
  nothing. A repeat with a *different amount* raises an alarm.
- **Nothing is ever deleted.** Even the database owner gets an error.
- **Amounts never change.** Nor do direction, channel or who created the row.
  Provider details such as the receipt can be filled in once (a pending STK
  row gets its receipt when the callback arrives) but never altered.
- Status only moves forward: `pending` → `succeeded` / `failed` /
  `cancelled` / `needs_review`, and `needs_review` → a final state.
- **Corrections are new rows.** A reversal is a new `out` row pointing at the
  original. It carries a reason, the name of the person who made it, and
  Safaricom's reversal receipt. A payment can be reversed only once.
- Every status change is written to `transaction_events`, together with the
  worker or person who caused it.

### allocation_batches and allocations
Each time money is applied, the system writes a **batch** (one decision) made
of **lines** ("KES 1,000 → INV-2041", "KES 500 → credit"). The database checks
three things:

- A payment batch's lines add up to **exactly** the payment amount. Nothing is
  lost and nothing is invented.
- A credit-application batch nets to zero (+x to a request, −x from credit).
- A transaction is allocated **at most once**. This is the second guard
  against duplicates.

A request's `amount_paid` and a payer's `credit_balance` are running totals
that **only these lines can change**. A direct UPDATE is refused. `talksasa-pay admin ledger check` confirms the
totals still equal the sum of the lines; it runs nightly once the worker
arrives in Phase 2.

### audit_log
Every sensitive action is recorded: product created, key issued or revoked,
webhook URL changed, payer created, reversal, and later every admin action.
Each row includes a fingerprint (SHA-256) of the row before it, forming a
chain. Editing or deleting a past row breaks the chain, and
`talksasa-pay admin audit verify` reports where.

### Staff accounts (admin panel)
`admin_users`, `admin_invitations`, `admin_sessions`, `admin_recovery_codes`
(migration `000002_admin`). Passwords are stored only as argon2id hashes, the
authenticator (TOTP) secret is encrypted with the master key, and session,
setup-link and recovery-code tokens are stored only as fingerprints, so a
database copy cannot be used to sign in. The database refuses to:

- delete any of these rows (staff are disabled, sessions revoked);
- mark an account active without a password and an authenticator;
- send an account back to "invited" without wiping its old credentials;
- change a session's expiry or stage, or revive a revoked session or used link.

See `docs/runbooks/admin-access.md` for how staff are onboarded and offboarded.

## Allocation rules (confirmed 2026-11-22)

When a payment arrives for a payer:

1. **Targeted first.** If it was started for a specific request (STK push or
   the hosted page) and that request is still payable, it pays that request
   first.
2. **Then oldest first.** Any remainder pays the payer's other open or
   partially paid requests, oldest first.
3. **Then credit.** Anything left becomes credit on the payer account.
4. **No money bounced.** A payment for a request that was cancelled or expired
   meanwhile is not rejected; it follows rules 2–3.
5. **Credit is used automatically.** When the product creates a new request,
   existing credit is applied straight away.
6. **Unmatched money waits.** If the account number matches nobody, the money
   is recorded with no payer and waits in suspense for an admin to assign it.

Examples: a KES 1,000 bill paid with 1,000 becomes `paid`. Paid with 400 it
becomes `partially_paid` (600 outstanding). Paid with 1,500 it becomes `paid`
and the payer holds KES 500 credit; the next KES 300 bill is then paid
instantly from that credit.

## Product isolation

Every query takes the product id from the authenticated API key, never from
the request. On top of that, the foreign keys include the product id, so the
database cannot store a payment request for product A that points at a payer
of product B, even if application code tried.

## Money

All amounts are whole Kenya shillings stored as integers (`bigint`). There are
no floats anywhere. Inputs such as `"100.50"` are rejected rather than rounded.
